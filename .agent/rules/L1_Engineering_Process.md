# L1 – Superpowers Engineering Process Rules

**Priority: HIGH (Level 1 - Guides how work is done)**

1.  **Workflow Discipline**: Non-trivial tasks must follow structured workflows (e.g., plan → implement → verify).
2.  **Mandatory Brainstorming**: Call `brainstorming` Skill before implementation when intent, technical design, or financial risk is unclear.
3.  **Mandatory Planning**: Call `writing-plans` Skill and get confirmation BEFORE modifying any code in `src/`.
4.  **TDD for Logic**: Use `test-driven-development` Skill for any changes to core logic (analyzer, position sizer, safety checks). Write tests before code.
5.  **Systematic Debugging**: Use `systematic-debugging` Skill for any bug report or unexpected behavior. Do not "guess" a fix.
6.  **Protocolized Code Review**: Before finalizing significant changes, use `requesting-code-review` Skill. You MUST define the scope using Git SHAs (`BASE_SHA` to `HEAD_SHA`) to ensure technical precision.
7.  **Defensive Reception**: When receiving feedback, follow `receiving-code-review` Skill. 
    - **Prohibited**: Performative agreement (e.g., "You're right", "Great point", "Thanks").
    - **Required**: Restate technical requirements, perform objective verification (grep/tests), and provide reasoned pushback if a suggestion violates YAGNI or project invariants.
8.  **Verification > Assertion**: Completion of a task requires hard verification (automated tests passing or log evidence), not mere assertion. Where automated tests are applicable to the changed behavior, they are necessary but never sufficient evidence for completion of cross-boundary, persistence, provenance, restart, safety, or authority changes. Passing tests generated by the executor themselves must not be accepted without verifying production call paths, boundary contracts, and negative fail-closed behavior. Any logic change from a review MUST be re-verified via TDD.
9.  **Syncing State**: Always inspect `configs/base.py` (and the relevant strategy module) at session start. Do NOT reference `src/main.py` or `src/config.py` — they do not exist in this project.
10. **Closure Revision Routing**: When revising a high-risk Design or Implementation Plan after Closure Audit or Closure Confirmation findings, MUST load and follow `.agent/skills/closure-revision/SKILL.md` before editing. If the proof graph, trust boundary, and scope are frozen, first build the complete blocker ledger, Mutable/No-Touch sets, and impact cones; then produce one coherent revision and an author-side mini Closure Confirmation. The author must not self-approve, expand frozen scope, or enable implementation, deployment, runtime, execution, paper-trading, or live-trading authority.
11. **Upstream Contract & Positive-Fixture Integrity**: All positive cross-module/cross-boundary fixtures and test assertions MUST derive from canonical upstream sources: (a) calling the canonical upstream constructor/serializer directly, (b) parsing upstream artifact bytes with the upstream strict loader, or (c) invoking registered upstream test fixture factories. Handcrafted dictionaries, arbitrary mocks, or synthetic placeholders (`req_1`, fake hashes, copy-pasting foreign attestations) that bypass upstream validation are strictly prohibited for positive boundary verification. Negative tests SHOULD use one declared mutation whenever that isolates the invariant; multi-point or multi-artifact mutation is permitted only when the approved lifecycle/state invariant itself requires a compound state, and every mutation must be explicitly enumerated and justified. Internal pure-logic unit tests within a single module may use local structures provided they do not cross module or artifact trust boundaries.
12. **Architectural Drift Fail-Closed & Escalation**: When execution encounters an impedance mismatch between upstream runtime behavior and the approved implementation plan, the executor MUST NOT invent local ad-hoc bypasses, synthetic fallbacks (e.g. `.get(key, default)` for missing provenance, synthetic hashes, copying attestation bytes), or layering violations (e.g. importing scripts into src). Instead, the executor MUST halt, classify the drift into one of three categories:
    - `BLOCKED_IMPLEMENTATION_DEFECT`: Local executor misunderstanding of approved design or existing API; fix locally within approved scope and plan without changing design.
    - `BLOCKED_SCOPE_DRIFT`: Implementation requires touching files or contracts outside the approved whitelist; halt and request plan/whitelist revision.
    - `BLOCKED_SPEC_DRIFT`: Approved design/plan has structural contradiction with frozen upstream reality; halt and escalate with a formal Evidence Packet (Failed Invariant, Upstream SSOT reference, Contradiction proof, Proposed architectural delta) back to the Design/Plan workflow.
