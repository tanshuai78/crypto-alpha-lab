# Audit Plan Completion

## Purpose

Prove that the approved Plan was fully implemented, verified, and kept within its allowed scope. Passing tests alone is not completion.

**REQUIRED SUB-SKILL:** Use `verification-before-completion` for fresh command evidence. For significant code changes, use `requesting-code-review` before the final verdict.

## Evidence Authority Hierarchy (8-Tier Authority Model)

When evaluating implementation completion and invariant satisfaction, the auditor must strictly prioritize evidence in the following descending order:

0. **Tier 0 (Highest / Normative Authority): Approved Design & Implementation Plan**: Approved Design, approved Delta Design, approved Implementation Plan, and explicit user authorization define what implementation is required and what authority is permitted. Lower tiers cannot silently override Tier 0. If real upstream/runtime evidence contradicts Tier 0, the auditor must classify specification/interface drift (`BLOCKED_SPEC_DRIFT`) and block completion rather than reinterpret the approved contract.
1. **Tier 1: Real Upstream Artifacts & Filesystem Bytes**: Actual bytes, hashes, disk permissions, locks, and payloads generated by upstream runtime or authorized tests on disk, proving whether requirements are implementable.
2. **Tier 2: Real Production Entry Points & Runner Call-Chains**: Verified invocation paths from CLI/runner scripts into `src/` core functions, ensuring code is wired into production execution and not orphaned.
3. **Tier 3: Independent Negative Probes & Mutation Tests**: Tests that actively mutate inputs, corrupted state, locks, or disk boundaries in isolated test environments to verify fail-closed defense.
4. **Tier 4: Positive Tests Derived from Canonical Upstream Serializers**: Positive contract tests built from upstream canonical constructors/serializers or strict loaders, rather than ad-hoc dictionaries.
5. **Tier 5: Static AST Differential Scan & Plan-Required Linters**: Output from `.agent/tools/anti_shortcut_scan.py` (and plan-required linters when explicitly specified in the approved Plan), proving absence of shortcuts, layering violations, syntax errors, and forged provenance.
6. **Tier 6: Executor Passing Test Logs**: Log output of tests written by the executor. This is necessary evidence where applicable, but NEVER sufficient evidence on its own.
7. **Tier 7 (Lowest / Strictly Unverifiable): Executor Assertions & Comments**: Verbal claims, explanations, docstrings, or checklist items claiming completion without code/runtime backing.

## Auditor Read-Only Invariant

The completion auditor operates strictly in **Read-Only** mode:
- **Prohibited**: The auditor may not persistently modify ANY project/repository file, fixture, test, documentation, config, runtime evidence root, or approved artifact. Ephemeral files may be created only under isolated temp directories for auditor-owned probes.
- **Required**: Documenting precise findings (P0/P1/P2) with file:line evidence and returning the appropriate verdict (`complete`, `incomplete`, or `blocked`). All remediation must be executed by the implementation/remediation agent under a controlled workflow.

## Verdicts

- **complete**: every Task, invariant, Done Definition item, compatibility obligation, and verification gate passes; scope is fully accounted for.
- **incomplete**: required implementation, wiring, serialization, tests, or documentation is missing. Any mandatory fix means incomplete.
- **blocked**: a P0 safety/scope failure exists, mandatory verification fails, or missing provenance/evidence prevents an honest audit.

Only `complete` permits a completion claim, commit, merge, or deployment.

## Required Inputs

1. Approved Design and Implementation Plan, including `Allowed Change Scope`.
2. `BASE_SHA` from immediately before execution.
3. Pre-execution `git status --short --untracked-files=all` snapshot, plus a patch or SHA-256 for every pre-existing dirty/untracked path that execution may overlap.
4. Current worktree and fresh verification results.

If the pre-execution snapshot is missing, label ownership as `scope_provenance_uncertain`. Do not attribute, revert, or overwrite an existing change. Return `blocked` when that uncertainty prevents full scope accounting.

## Audit Flow

### 1. Capture the Entire Change Set

Verify the base and inspect committed, staged, unstaged, and untracked files:

```bash
git merge-base --is-ancestor "$BASE_SHA" HEAD
git status --short --untracked-files=all
git diff --name-status "$BASE_SHA"
git diff --cached --name-status "$BASE_SHA"
git diff --name-status
git ls-files --others --exclude-standard
```

Inspect both index and worktree diffs. A staged change can be reversed only in the worktree, making the final file match `BASE_SHA` while the index still differs. Do not use `<base>...HEAD` as the only source; it misses current worktree and untracked changes.

Never run `git checkout`, `git reset`, `git clean`, or any other destructive remediation automatically. Report exact paths and ownership evidence; the user decides whether to preserve, split, or revert them.

### 2. Enforce Allowed Change Scope

Classify every changed path against:

- `Allowed implementation paths`
- `Allowed verification paths`
- `Allowed documentation paths`
- `Allowed generated/runtime artifacts`
- `Affected but unchanged`
- `Forbidden`

Bounded legacy labels are acceptable. An unchanged compatible consumer is not a scope violation; require its stated regression/integration evidence. Verify generated artifacts exist when required and remain ignored or uncommitted unless the Plan explicitly allows committing them.

A proven task-induced change outside allowed paths is a P0 scope blocker. A pre-existing user change is preserved and excluded from task attribution.

### 3. Map Plan to Implementation

Build a matrix before judging completion:

```text
Task / invariant | Required artifact | Implementation evidence | Production wiring evidence | Fresh verification | Status
```

Check every Task, design invariant, Done Definition item, serializer/state field, restart path, production entry point, deployment command, and documentation deliverable. A helper that exists only in `src/` and tests but is not called by the required production path is incomplete.

Inspect new tests to confirm they assert the planned behavior and failure branch; test count alone is not evidence.

#### 3.1 Critical Invariant-to-Runtime & Mechanical Evidence Mapping
Do NOT accept a test containing an invariant name as proof of invariant satisfaction.
- **Critical Runtime Invariants (P0-capable)**: For every safety, authority, or lifecycle invariant (e.g. fail-closed state persistence, storage/memory budget reservations, exclusive/shared writer locks, crash restart recovery boundaries): require concrete production enforcement and live call-order evidence in `src/` and runner orchestration.
- **Other Invariants**: Require the appropriate mechanical evidence class:
  - Production code `file:line` (runtime calculation/validation logic),
  - Config `file:line` (SSOT constants/thresholds in `configs/base.py`),
  - Deployment command/flag (process invocation semantics),
  - Serializer/validator artifact (schema/manifest byte integrity),
  - Static absence proof (AST / `rg` proving absence of forbidden calls, e.g. absence of private API),
  - Documentation artifact (reviewed specification deliverable).
Do not manufacture fake runtime line mappings for invariants whose canonical proof is structural or absence-based.

#### 3.2 Fixture Provenance Audit
Audit the provenance of all positive test fixtures used in cross-module boundary tests:
- Positive contract fixtures MUST derive from canonical upstream sources: direct calls to upstream dataclass/model constructors, upstream canonical serializers, or artifact bytes validated by upstream strict loaders.
- Strictly check for and reject:
  - Arbitrary hand-crafted dictionaries that bypass upstream field validation;
  - Synthetic or invented fallback strings (`req_1`, `rev_1`, fake hash mappings);
  - Direct byte copying of upstream attestations or secrets to fabricate downstream artifacts.
Any positive boundary test relying on unverified or fabricated fixtures has ZERO evidentiary value; mark the associated task/invariant as `incomplete` or `blocked`.

#### 3.3 Auditor-Owned Negative Probing & Authority Boundary
The auditor must independently verify fail-closed defense at critical boundaries:
- For key authority gates, format checks, lock contention paths, and corrupted storage states, verify that corrupt, incomplete, or unauthorized inputs trigger immediate fail-closed termination.
- Confirm that errors are not swallowed, converted into silent fallback defaults, or masked by permissive dictionary `.get()` lookups.

**Negative Probing Authority Boundary (Hard Safety Constraint)**:
Auditor-owned negative probes MUST default to isolated tempdirs, offline fixtures, test doubles, or disposable test roots.
The auditor MUST NOT:
- mutate production/runtime evidence roots,
- mutate upstream sealed evidence,
- invoke real public/private network,
- start deployment/runtime processes,
- acquire deployment authority,
unless that exact action is separately authorized by the approved Plan and explicit user authorization.

### 4. Recheck Topology and Contracts

For changed shared helpers, SSOT functions, contracts, schemas, CLI flags, or transport fields:

1. Confirm `graphify-out/graph.json` matches the reviewed baseline; otherwise treat it as advisory.
2. Run targeted `graphify query "<exact_symbol>"` or `graphify path "<producer>" "<consumer>"`.
3. Verify every candidate edge at source lines.
4. Use `rg` for changed JSON keys, JSONL fields, event types, CLI flags, and paths because call graphs can miss transport consumers.

Graphify discovers impact; it does not prove correctness. A clean, stale, `INFERRED`, or `AMBIGUOUS` result never proves that no consumer exists.

### 5. Check Minimality and Side Effects

Apply Ponytail only inside the approved requirements: flag duplicate helpers, speculative abstractions, unnecessary dependencies, and unrelated formatting/refactors. Do not simplify away safety validation, idempotency, restart recovery, compatibility, SSOT boundaries, or approved Design invariants.

### 6. Run Fresh Verification

Run the exact targeted tests and non-mutating checks required by the Plan, then:

```bash
git diff --check "$BASE_SHA"
git diff --cached --check "$BASE_SHA"
git diff --check
python3 .agent/tools/anti_shortcut_scan.py --base-sha "$BASE_SHA"
```

The AST differential anti-shortcut scanner must run against `$BASE_SHA` across all committed, staged, unstaged, and untracked changes:
- Any non-zero exit code (including syntax errors, read failures, scanner integrity errors, or AST shortcut errors) is a P0 blocker and results in an immediate `blocked` verdict.
- All `WARNING` findings must have explicit justifications in the Task scanner disposition ledger; any un-disposed warning results in an `incomplete` verdict.

Apply deployment and safety checks only to affected paths and invariants. Do not scan all historical docs and demand zero matches.

For this repository, always verify the master switch directly:

```bash
PYTHONPATH=src:. .venv/bin/python - <<'PY'
from configs import base
assert base.RISK_LIVE_TRADING_ENABLED is False
PY
```

If deployment files changed, inspect actual command/process arguments. An executable `events/\*.jsonl` argument that prevents future-file discovery is a P0 deployment blocker, not a documentation-only warning.

## Output

Report findings first, ordered P0/P1/P2, then:

1. Verdict: `complete`, `incomplete`, or `blocked`.
2. Scope matrix: allowed, actual, pre-existing, unapproved, provenance-uncertain.
3. Task/invariant matrix with file:line evidence.
4. Topology/contract evidence, including Graphify limits and `rg` results.
5. Fresh commands, exit codes, pass/fail counts.
6. Required actions and residual risks.

Do not claim 100% scope compliance when provenance is uncertain. Do not call work complete while required fixes remain.

See `PRESSURE_TESTS.md` for RED/GREEN validation scenarios.
