## 核心结论

工作区重构方向**总体正确**，相比原始九条并行的事件源路线，新设计更加符合个人投资者的真实工程约束与风险承受能力。但并非所有设想均可直接成立，需遵循以下修正判定：

```yaml
decision: approve_research_realignment_with_material_revisions

# Stage 1.6 定位：Futures Delisting 当前研究主线，而非已确认的独立 Alpha

# Stage 1.6R 定位：L0 准入网关，禁止授予自动平仓等自主控制权
stage1_6r: high_value_shadow_risk_veto
stage1_6r_l0_autonomous_control: forbidden

# 整合规则

# 裁剪/冻结路线

prediction_market: downgraded          # 预测市场：降级为宏观参考
governance_quant_pipeline: killed      # 治理量化管线：放弃
```

> [!IMPORTANT]
> **三大核心修正项**：
> 1. **Stage 1.6（期货下架）是当前最高优先级研究主线，并非已验证的独立 Alpha。**
> 2. **1.6R（安全事故）应当作为 L0 风控的输入传感器与准入闸门 (Admission Gate)，绝对不能直接调用执行器执行自动平仓。**
> 3. **ETF 流入与交易所净头寸只能在最顶层 (Regime Output) 进行决策层合并，严禁过早共用底层数据、时间戳或验证管线。**

## 一、 基本立场修正：降低先验，而非预先排除

将事件源的研究重点从“公告发布后预测短期涨跌”升级为“规则驱动强制流、市场状态过滤器与风险一票否决”是正确的结构升级。原路线总纲中确立的“公开数据、保守 `available_at_ms`、1 小时以上二阶反应、真实成本与基线对比、Live Depth Evidence 校验”等标准应当继续作为统一门槛。

但以下表述过于绝对：
> *“所有事件源研究的核心定位必须从方向性 Alpha 转变为强流、过滤器和 Risk-Veto。”*

更准确的研究哲学应定义为：

```yaml
default_prior:
  事件源默认不具备可执行的方向性 Alpha

first_research_target:
  侧重于 source integrity / liquidity / volatility / forced flow / risk regime

directional_effect:
  允许作为辅助诊断指标 (secondary diagnostic)
  只有在独立通过 baseline、真实交易成本、持仓集中度以及 live depth 检验后，才能升级为方向性信号
```

> [!NOTE]
> 不能仅因为历史中多数公告事件没有即时方向 Alpha，就在研究阶段预先排除较慢的价格漂移可能性。**正确的学术与实盘态度是“调低先验概率”，而非“物理隔离”。**

## 二、 Stage 1.6 (期货下架)：强制流机制不等于方向性收益

### 2.1 优先级排序合理的依据
`Stage 1.6` 具有清晰的工程可行性，适合作为第一优先级：
* **数据可审计**：官方公告语义明确，便于追踪。
* **技术复用度高**：可直接复用 `Stage 1.5` 建立的公告解析、Symbol Mapping、Watermark 推进和 Depth 监控管线。
* **生命周期规范**：合约下架具有明确的时间表，研究可以聚焦于“公告发布”、“限制新开仓”、“最后结算”三个时间窗口。
* **非高频竞争**：无需参与公告发布后第 1 秒的毫秒级争夺。

近期交易所的下架公告也证实了结构性强制流的存在：
* 自动关闭并结算全部仓位；
* 结算前禁止新开非 `reduce-only` 仓位（部分公告表现为禁止所有新订单）；
* 结算前最后一小时保险基金可能退出清算支持；
* 清算可能通过单次 `IOC` (Immediate-Or-Cancel) 订单向市场强行卸载，未成交部分可能直接触发 `ADL` (自动减仓)；
* 交易所保留临时调整杠杆、保证金、Funding Rate、指数成分及 Mark Price 机制的权利。

这证明了：
$$\text{forced processing mechanism} = \text{real}$$
$$\text{liquidity / liquidation risk} = \text{real}$$
$$\text{rule-defined timetable} = \text{real}$$

> [!WARNING]
> 以上机制的真实存在，**并不能推导**出：
> 1. 价格方向必然单边下跌；
> 2. `T+1h` 盲空具有稳定 Edge；
> 3. `T-24h` 至 `T-1h` 窗口具有可执行性；
> 4. 结算收敛效应一定能够压过 Squeeze 风险。
>
> 事实上，结算前最后一小时保险基金退出和流动性断崖意味着尾部路径极易发生非连续跳空。

### 2.2 核心研究误区：处理变量内生性 (Treatment Endogeneity)
下架标的在公告前通常已呈现出：**长期流动性衰退、成交量大幅萎缩、项目方基本面恶化、价格处于下行通道、已被挂牌 Monitoring Tag 等特征**。

因此，观察到下架公告后价格继续走低，极有可能是既有趋势的惯性延续：
$$\text{pre\_existing\_distress\_continuation}$$
而非下架公告本身的独立增量效应：
$$\text{incremental\_delisting\_effect}$$

> [!IMPORTANT]
> **设计中必须引入精准匹配基线**：
> 不能仅使用随机事件或 BTC 指数作为 baseline，必须构建包含以下特征的**控制组 (Matched Controls)**：
> - 相似市值与公告前 $7\text{d} / 30\text{d}$ 价格动量；
> - 相似的成交量衰减斜率与 Spread/Depth 深度；
> - 相似的 Funding Rate 和 Open Interest (OI) 结构；
> - 相似的交易所挂牌覆盖面。

### 2.3 扩充 timetable 时间语义字段
现有的三个时间锚点假设过于单一，无法适应不同交易所公告的语义差异。建议在 Schema 中进行如下扩充：

```python
# 时间戳字段
source_published_at_ms: int             # 官方发布时间
first_observed_at_ms: int               # 首次检测时间
available_at_ms: int                    # 详情页可用时间
announcement_revision_at_ms: int         # 公告最后更新时间

order_restriction_start_ms: int         # 开仓受限生效时间
order_restriction_type: str             # 限制类型: reduce_only_only | no_new_positions | no_new_orders | unknown

final_hour_start_ms: int                # 保险基金政策变化/波动高发临界时间
settlement_time_ms: int                 # 结算价格锁定时间
delisting_complete_time_ms: int         # 合约完全下架时间

# 机制属性字段
contract_margin_family: str             # USD_M | COIN_M
delisting_scope: str                    # contract_only (仅下架合约) | token_wide (现货及全面下架)
automatic_settlement: bool              # 是否自动结算
settlement_price_basis: str             # 结算价计算基准
index_constituent_change_possible: bool # 是否可能临时调整指数成分
insurance_fund_final_hour_policy: str   # 尾部清算保险基金政策
ioc_liquidation_policy: bool            # 是否强行使用 IOC 清算
adl_possible: bool                      # 是否可能触发自动减仓
protective_parameter_change_possible: bool # 交易所是否保留临时更改风险参数的权力
```

### 2.4 指标优化优先级
在 Stage 1.6 的研究第一阶段，应当以**强制流与流动性诊断**为主指标，**价格方向**为次指标：

* **P0 级指标（数据源完整性）**：`source coverage`, `product classification accuracy`, `timestamp coverage`, `revision integrity`, `historical market existence`
* **P1 级指标（流动性与波动特征）**：`spread expansion`, `depth collapse`, `book availability`, `mark-index divergence`, `realized volatility`, `wick / MAE` (最大回撤与上影线), `funding and OI decay`
* **P2 级指标（方向性收益）**：`forward return` (前向收益), `baseline excess return` (基线超额收益)

## 三、 Stage 1.6R (安全事故)：安全传感器而非自动化平仓执行器

```text
安全避险的成功判据 != 方向性做空收益
```

路线设计中对于“禁止主动 exploit short、禁止在 Depeg 时进行动量交易、禁止未经多方确证的推特传闻触发”等规定是完全正确的。但需明确定义其系统层定位：

### 3.1 外部事件源严禁成为 L0 自动执行路径
`Actuator`（执行动作器）具有最高执行权限。如果未经链上或官方渠道 100% 确认的事故源能够直接触发自动平仓或全局强制降杠杆，那么**假消息、资产错误映射或 API 解析异常将直接导致策略出现非预期亏损**。

> [!CAUTION]
> **正确的 Risk-Veto 架构应为级联式的半自动网关：**
> 
> ```mermaid
> graph TD
>   A[Incident Source] --> B[Confirmation State Check]
>   B --> C[Exposure Mapping]
>   C --> D[Shadow Risk-Veto]
>   D --> E[Block New Admission & Risk Budget = 0]
>   E --> F[Manual Protective Review / Admin Override]
> ```
> 
> * **第一版允许的自动动作**：禁止 Affected Scope 新开仓、将受影响资产的 Risk Budget 设为 0、阻止新挂单生成。
> * **第一版严禁的自动动作**：自动调用市价单平仓 (`automatic_market_exit`)、自动强制全局减仓、自动触发 Order Executor 执行清算。

### 3.2 冷却期应基于状态机解锁，而非固定 60 分钟
不同的安全事件（如 Stablecoin depeg、Bridge hack、Chain halt、Exchange insolvency、Oracle failure）恢复周期跨度极大（从数分钟到数周不等），固定 60 分钟冷却期缺乏数据支持。

建议引入“冷却状态机”：

```text
WATCH (观察期)
  └── CONFIRMED (确认事故)
        └── VETO_ACTIVE (否决激活)
              └── RECOVERY_PROBATION (恢复期观察)
                    └── CLEARED (解除警报) 或 RETRACTED_FALSE_ALARM (确认为误报)
```

**解除 Veto 状态需满足的多 venue 联动条件**：
* 官方发布确认恢复的公告；
* 链上共识与区块生产恢复正常 (`chain_finality_restored`)；
* 受影响交易所的充提通道状态恢复；
* 多市场差价 (Multi-venue spread) 回归历史正常分位数；
* 盘口深度 (Depth recovery ratio) 恢复至事件前 $80\%$ 以上。

### 3.3 指标完善与权衡 (Trade-Off)
安全否决模块应当新增以下评估指标：
* `confirmation_latency_ms`：事件从发生到否决生效的延迟；
* `market_dislocation_before_confirmation_ms`：否决生效前市场已产生的偏离度；
* `affected_asset_mapping_precision / recall`：受影响资产映射的精确率与召回率；
* `false_positive / negative_rate`：误报率与漏报率；
* `veto_opportunity_cost`：误报导致的策略停机机会成本。

## 四、 1.6B + 1.6F (ETF 与交易所头寸)：数据面物理隔离，决策层统一接口

将 `ETF Flow` 与 `Exchange Net Position` 整合为“每日资金与供给流向诊断”符合宏观逻辑，但两者的数据特征存在本质差异，不应共用底层的清洗与流水线。

| 维度 | ETF Flow | Exchange Net Position |
| :--- | :--- | :--- |
| **数据频率** | 日频 (Daily) | 日频聚合，但底层链上数据为连续 Tick |
| **时间语义** | 官方报告发布/更新时间 | 区块高度时间 (Block time) / Indexer 时间 |
| **修订风险** | 发行方历史数据修正 | 地址标签归属变更、内部大额冷钱包转账修订 |
| **主要偏差** | 价格同期性内生偏差、发行方集中度 | 地址归集误差、托管迁移与跨链包装代币噪音 |
| **资产范围** | 仅限于 BTC / ETH | 首期仅建议分析 BTC |

### 4.1 推荐的隔离架构
```text
ETFFlowSourceAdapter (独立采集)
  └── etf_flow_daily_state
                                ├──> DailyCapitalSupplyRegimeComposer (顶层合并) -> combined_regime_label
ExchangePositionSourceAdapter (独立采集)
  └── exchange_supply_daily_state
```

> [!IMPORTANT]
> - 严禁共用 `available_at_ms` 与数据源完整性 (Source integrity) 阈值。
> - 严禁在各自因子独立通过数据审计前进行过早的“特征交叉”与“权重调优”。

### 4.2 验证机制与消融实验 (Ablation Test)
因子有效性验证必须遵循严谨的先后顺序：
1. 验证 ETF 因子单独的 Source Audit 与稳健性；
2. 验证 交易所净头寸 因子单独的 Source Audit 与稳健性；
3. 对两因子使用相同宏观资产回报进行残差化 (`residualization`) 剥离价格同步噪音；
4. 进行 walk-forward 前向验证；
5. 执行消融实验 (`ablation`)，确保组合后的效果明显优于单因子：
   $$\text{combined\_uplift} > \max(\text{etf\_only\_uplift}, \text{exchange\_position\_only\_uplift})$$

## 五、 1.6E + 1.6G (杠杆与情绪)：归入同一命名空间，输出保持独立

这两者在信息属性和反映的市场周期上差异显著，严禁合成单一的“辅助过滤器分数”。

* **1.6E (杠杆通道公告)**：反映杠杆获取的难易度，属于小时级的离散公告事件，可能直接引起 Funding/OI 的瞬间结构调整。
* **1.6G (恐慌贪婪与趋势)**：反映市场中长期的慢速情绪，主要由价格动量和历史波动率计算得出，极易与策略已有的 BTC 市场 Regime 变量高度共线性。

### 推荐实现方式
可以将代码存放在统一目录下：`src/research/auxiliary_filters/`。但在调用接口层，输出必须保持完全解耦：

```python
leverage_access_shock_context: dict # 杠杆变动冲击上下文
sentiment_extreme_context: dict     # 情绪极值上下文
narrative_attention_context: dict   # 社交趋势热度上下文
```

> [!CAUTION]
> 严禁在第一版中采用复合加权分数的做法（例如：`0.5 * margin + 0.3 * F&G + 0.2 * Google Trends`）。这种设计会赋予回测过高的自由度，导致研究人员通过微调权重来“凑出”回测盈利，从而掩盖单因子实盘失效的真相。
>
> 此外，Google Trends 属于相对缩放数据，其历史数据窗口和查询方式的微小变化都会彻底改变特征数值，在工程上难以实现点对点的时间回溯一致性 (Point-in-time consistency)。

## 六、 放弃与冻结路线的界限划分

### 6.1 1.6H Spot Listing (现货上线) —— 确定放弃 Alpha 管线
同意放弃现货上线作为主动交易因子。因为在现货层面，个人投资者在流动性、手续费摩擦及与做市商竞争中没有任何优势。
* **保留价值**：将 Stage 1.5 积累的期货上线数据作为**阴性对照组 (Negative Control)**、交易纪律案例库以及挂牌分类参考。

### 6.2 复杂社交音量 —— 彻底废弃
完全同意彻底裁撤 LunarCrush、Santiment 社交音量统计、Twitter 爬虫、KOL 情绪打分以及 Telegram/Discord 信号分析管线。
* **判定依据**：对于个人项目，此类数据维护成本极高、数据源历史不可追溯、水军与 Bot 操纵严重，且存在频繁的结构漂移，期望收益远低于开发成本。

### 6.3 1.6D Unlock (代币解锁) —— 冻结 Replay 验证
同意冻结该 Replay 验证。代币解锁并不等同于代币被即时抛售，且存在复杂的锁仓修改、Vesting 变更和场外OTC交易。
* **数据门槛修正**：无需自建 Ethereum/Solana 归档节点。可接受的替代方案包括“具备历史修订版本的商业供应商快照”或“直接审计 Vesting 智能合约日志+官方公告”。
* **行动建议**：分配最多 2~4 小时进行数据可行性评估，若无法低成本获取无未来偏差的历史 point-in-time 解锁快照，则直接关闭该项目。

### 6.4 1.6C Prediction Market (预测市场) —— 降级为宏观背景参考
仅保留其作为宏观上下文、高流动性合约（如选举、特定监管事件）的定性观察。不建立任何量化 Replay 或交易执行管线。

### 6.5 1.6I Governance (治理事件) —— 降级为事件驱动型低频复盘
放弃固定按季度机械式地分析全部提案。将其改为：当策略持有受重大提案影响的协议暴露时，触发定向人工评估与提案阅读，其余情况保持低频跟踪。

## 七、 术语体系修正：区分“研究候选”与“验证策略”

为防止在未来策略报告和合规审查中出现语义漂移，重构后的主策略线（目前包含 Extreme Funding、Trend/Liquidation、Long-Horizon Basis）由于当前在实盘中尚未有实际交易额度，必须在 Roadmap 中明确归类为：

```text
[既有策略观察线 / Observation-Only Strategy Research]
```

只有在实盘影子系统 (Shadow Mode) 或小额实盘中稳定运行通过一个策略周期后，方可升级为 **Active Strategies** 或 **Validated Strategies**。

## 八、 已验方法论 vs 待验假设

在推进 Stage 1.6 重构时，必须严格区分哪些工具和方法论是项目已经验证有效的，哪些仍处于假设阶段。

### 项目已验证有效的方法论 (Proven Methodology)
1. **Source-First 优先验证原则**：在 `Stage 1.5` 中通过对详情页延迟、解析逻辑、Launch Anchor 偏移和 Watermark 污染的排查，证明了“先审计数据源可用时间、后开发信号”的工程步骤能有效降低伪 Alpha 的发生概率。
2. **Clean / Quarantine / Invalid 分层设计**：证明了将事件分类隔离、避免将“有数据”简单等同于“可直接交易”的必要性。
